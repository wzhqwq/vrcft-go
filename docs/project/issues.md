# Issue Tracker

Manually track issues discovered during development and reported by the open-source community, including progress, verification results, and archive history. This file is not generated by `projectstatus`; acceptance requirements remain defined by designs, plans, and package/subsystem specifications.

## Quick Entry

1. Search this file, including archived entries, for matching keywords or community links before adding an issue.
2. Copy the template below into the appropriate active section. Use `DEV-0001` for development findings and `COM-0001` for community issues. Increment each sequence independently, keep IDs unique across active and archived entries, and never reuse an ID.
3. Fill in the ID, title, discovery date, and description to record an issue. Other fields can keep their defaults. Use `YYYY-MM-DD` for dates.
4. As work progresses, update the status, updated date, and next action. When work ends, record the end date, resolution or closure reason, and verification evidence.

Classify the source by where the issue was first discovered. If a development finding is later reported to the community, add the link to the existing entry without changing its ID. Add duplicate reports to the same entry. Community issues include user reports for this project and issues in upstream or dependency projects that affect this project. Record the project and original issue link, or the reporting channel if no link is available.

## Status Conventions

| Status | Meaning and required updates |
| --- | --- |
| `unconfirmed` | Newly recorded; reproduction or impact assessment is pending. |
| `open` | Confirmed; work has not started. |
| `in_progress` | A fix or follow-up is underway; record the next action. |
| `blocked` | Progress cannot continue; record the blocker, dependency, and next review date. |
| `pending_verification` | A fix has been submitted or an upstream solution is available; verification in this project is pending. |
| `resolved` | Verified as fixed in this project; record the version or commit and verification results. |
| `closed` | No further work is planned; record the reason, such as duplicate (with the original ID), not applicable, or a decision not to fix. |

The usual flow is `unconfirmed` -> `open` -> `in_progress` -> `pending_verification` -> `resolved`. Use `blocked` or `closed` as appropriate. Failed verification returns an issue to `in_progress`. Closure of a community issue does not establish resolution in this project; check the dependency version, integration, and verification results.

Archiving changes an entry's location, not its status. If an issue recurs, move the original entry back to its active section, preserve its ID and history, set it to `unconfirmed` or `open`, and record the reopening date and reason.

## Manual Entry Template

Copy the entire entry and replace the angle-bracket placeholders. Use `COM` instead of `DEV` for community issues. For complex issues, append reproduction steps, logs, or checklists directly to the entry; no separate index table is required.

```markdown
### DEV-<four-digit number> · <Issue title>

- Status: unconfirmed
- Discovered: <YYYY-MM-DD>
- Updated: Not yet updated
- Owner: Unassigned
- Affected scope: Not yet assessed
- Source/links: Not yet recorded (code location, community project and issue URL, related IDs or PRs)
- Description: <Observed behavior; include reproduction steps and expected versus actual behavior when known>
- Next action: Confirm the issue and assess its impact
- End date: —
- Resolution/closure reason: —
- Verification evidence: — (check commands and results, version/commit, or manual verification records)
- History:
  - <YYYY-MM-DD>: Recorded.
```

## Periodic Review and Archiving

- Review this file during its first maintenance update each month, and review active issues before a release. Maintainers perform this process manually; archiving is not automatic.
- Review each active entry's status and next action, and record community updates. Blocked issues should have a specific next review date. Keep unresolved issues active regardless of inactivity.
- Move complete `resolved` and `closed` entries whose end dates precede the first day of the current month into the archive below. Group them by the month of archiving, for example `### 2026-10`. Change entry headings to level four, such as `#### DEV-0001 · Title`, and preserve every field and history item.
- Remove the original active entries after moving them to avoid duplicates. Preserve IDs, sources, end dates, and resolution or closure evidence. Resolved issues require verification evidence; closed issues require a closure reason. Complete any missing information before archiving.
- Update the last review date below after each review, even if no entries qualify for archiving. If the archive becomes large, move monthly groups to `issues-archive/YYYY-MM.md` and retain relative links here. Reopening still moves the original entry back to its active section.
